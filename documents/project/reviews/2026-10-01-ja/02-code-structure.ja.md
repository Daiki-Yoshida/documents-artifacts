# コード構造

関連する境界がすでに選定されている場合に、一般的なコード編成について読むファイルです。

## クラスの分類ではなく、境界のある単位を実現する

ソフトウェアは、明示的な契約を通じて相互作用する、境界のある単位として扱ってください。

クラス、インターフェース、オブジェクト、関数、パッケージ、サービスは、いずれも実現手段です。設計の目標は、実装の詳細を隠し、偶発的な結合を減らし、変更の影響範囲を局所化することです。

境界の契約が保たれる限り、実装は置き換え可能です。

## まず機能／モジュールで分ける

必要に応じて内部に技術レイヤーを設けつつ、主要なコード境界には機能／モジュールを優先してください。

```text
<feature>/
  domain/
  application/
  infrastructure/
  ui/
```

小さなモジュールはフラットな構成のままでもかまいません。ディレクトリの数を増やすことが目標ではありません。

## レイヤーの責務

**Domain**
- ビジネス概念、不変条件、ポリシー
- UI／インフラストラクチャ／ベンダーへの依存を持たない

**Application**
- ユースケースとオーケストレーション
- ユースケース固有のポートを所有する
- 認可、トランザクション、ポート呼び出し、マッピングを調整してもよい
- Domain の不変条件や技術的な実装詳細を取り込まない

**Infrastructure**
- DB／HTTP／ファイルシステム／キュー、および技術的な実装
- プロジェクト所有の契約／ポートを実装する
- 技術的な型／エラーが内側へ漏れる前に変換する

**UI**
- プレゼンテーション、ビュー状態、入出力の書式設定
- 同じデプロイ単位／ランタイムにある場合は、Application に依存する。UI が別ランタイム（例: SPA + API）で動く場合は、独立した境界づけられたコンテキストとして扱う。「`TESTING.md` → Runtime seams」を参照
- プレゼンテーション用の型を Domain／Application に持ち込まない

**調整すること ≠ 所有すること。** ユースケースは、複数の責務を調整しても、それぞれの内部判断を引き受けるとは限りません。

## 契約の配置

契約は、その**存在理由**を所有する場所に配置してください。

```yaml
domain_contract: "Domain"
use_case_port: "Application"
technical_implementation: "Infrastructure"
```

すべてのインターフェースを Domain に集めないでください。

## 公開面

境界が堅牢化されたモジュールでは、通常、主要な公開面を小さく保ち、残りは内部に留めます。

- モジュールをまたぐアクセスは公開面を経由する
- 内部への深いインポートを避ける
- インフラストラクチャのアダプターは、通常、公開しない
- 必要なユースケース、契約、境界DTO、ファクトリーなどだけを公開する

追加の公開面には、対象となる利用者、安定性の範囲、進化のルールを明示する必要があります。

## 副作用は封じ込める。否定しない

状態、I/O、時間、外部システムは、実際のソフトウェアでは避けられません。

目標は、副作用を次のようにすることです。

- 所有する境界の中に隔離する
- 呼び出し側が依存する場合は明示する
- 追跡可能で、他へ伝播しない

副作用を隠したり、無関係なレイヤーへ押し込んだりして「純粋性」を追求しないでください。

## 共有配置

汎用の `shared` 置き場をひとつ作らないでください。

複数の利用側と、十分に安定した意味上の同一性が確認されてから、コード／概念を共有の場所へ昇格させてください。概念は、物理的に共有コードとして切り出されていなくても、利用側に依存しないものになり得ます。「`../design/CONCEPT_ALTITUDE.md`」を参照してください。

## 内部の自由度

正しい境界の内側では、状況に応じて手続き型、関数型、データ指向、最適化された低水準のコードを使用できます。

内部の優雅さを、境界の明確さ、外部に対する安定性、変更の局所性、または副作用の明示より優先しないでください。
