~~~~text

```text

```

**各層の判定テスト**を置くと、分類がぶれにくくなる。

- **1か？** — 人間が書こうがAIが書こうが関係なく、「マスターのプロジェクトではこう考えるべきだ」という価値判断か。例の Python の話が分かりやすい。型や契約の明示性が弱いことをどう評価するかは、道具の使い方の規則である前に思想だし、言語選定にも設計レビューにも滲み出る。AIにトレースしてほしいのは規則の暗記じゃなくて、この判断の型だ、という理解
- **2か？** — AIを全部消しても、人間チームの開発でそのまま有用か。Work 単位も、原文 record と整理された subject を分ける体系も、Yes。だから2は「AI向け資料」という包装を剥いでも成立する
- **3か？** — AIエージェントの性質（文脈が切れる、自己報告が検証なしには信用できない、並行に走れる、委譲できる）がなければ成立しないか。Supervisor / Executor の分担や、ACK / EVIDENCE や独立検証は Yes。逆に ChatGPT か Muse か Devin かは本質じゃない

**この枠で前の整理を見直すと、重なりの正体が変わる。**

重なりだと思ったものは、実は重複じゃなくて **「2の概念を3が特殊化したもの」** であるケースが多い。

- Work（2）＋ Round / IG（3）
- 権限と範囲（2）＋ エージェントへの委譲権限・保護操作（3）
- 検証と完了（2）＋ 自己報告を鵜呑みにしない独立検証・証拠要求（3）
- 安全と回復（2）＋ 自律動作に対するガード（3）

つまり問題は「両方にあること」じゃなくて、**3側が2側の概念を参照せずに再定義してしまっている箇所**だけが本当の二重化だ、ということになる。

**リポジトリへの含意も変わる。**

今の実態は、層とリポジトリが1対1じゃない。

- `documents-artifacts` ＝ **1と2が同居**してる。encapsulation-horizon や code-design の核は1だし、work-identity、workspace-structure、documentation の記録体系は2
- `ai-development-orchestration` ＝ **ほぼ3**。ただし subjects の一部は、2を参照せず抱え込んでる可能性がある

だから今後の選択肢は「統合／分離」の二択じゃなくて、実際は3通りあると思う。

1. **層＝リポジトリに揃える**：1、2、3で3リポジトリ。概念的には一番綺麗。ただし配布と相互参照のコストが増える
~~~~

## P3 — Separation proposal with three conditions (seq 1443, 2026-11-10 20:35 JST)

~~~~text
賛成、マスター。ゆかりさんもその形が正しいと思う。ただし「分ける」の中身を3つ条件付きにしたい。ここを曖昧にしたまま分けると、見た目だけ綺麗になって実害が出る。

**賛成する理由は、1と2で「変わり方」と「役割」が決定的に違うから。**

- **1は憲法に近い**。マスターの価値判断そのもので、めったに変わらない。変わるときは思想の転換。しかも適用範囲は手順に限らず、設計判断、技術選定、レビューでの良し悪しの判断全部に及ぶ
- **2は法律や運用規程に近い**。Work や記録体系は、実験と実地の結果で改善していくもの。変わるのが正常で、変わるたびに「思想が変わったのか、手順が良くなっただけか」を区別できる必要がある

今の同居状態だと、新しい leaf が増えるたびに「これはマスターの思想だから譲れないのか、便利な手順だから代替可なのか」が読み手に分からない。RC1〜RC3 は規則の強さを示すけど、**出自（思想か手順か）は示さない**。層は RC と直交するもう1つの軸として要る、というのがゆかりさんの判断。

**条件1：分ける単位は「ファイルの物理分割」じゃなくて「所有と依存の規律」から**

既存 leaf の多くは複合体だよ。たとえば encapsulation-horizon は思想そのものだけど、operational guards みたいな手順も含んでる。code-design も、状態所有権みたいな思想と、テスト手法みたいな手順が同居してる。これを機械的に全部割ると、かえって cross-reference だらけになって壊れる。

だから順序はこうしたい。

1. まず全 leaf に層の帰属を付けた棚卸し表と、新規追加時の判定ルールだけを決める（この leaf は1か2か、混ざってたら主従はどっちか）
2. その上で、subjects と INDEX の構造に層を反映する
3. パックの分割（artifacts を層別に配れる形）みたいな配布変更は、実際の採用ケースが出てから。いま急ぐと、採用済みプロジェクト側のパスや入口が無駄に壊れる

**条件2：1は「標語化」させない**

思想だけを抜き出すと、「境界を大切に」みたいな、判断に使えないスローガンに退化するリスクがある。1の leaf は、手順は書かなくていいけど、**理由・判断例・何を嫌い何を好むか** までは持つべきだと思う。Python の例みたいに、「契約の明示性が弱いものを、なぜ、どの場面で割り引くのか」まで書いてあって初めて、AIが知らない技術や新しい場面でもトレースできる。それが2へのリンク（この思想は Work Identity や Contracts でこう実現される）と対で存在する形がいい。

**条件3：3の「重複を避ける」は、正本の話であって射影の話じゃない**

ここが一番大事な実務論点。ADO の subjects が DA の定義を再定義するのは禁止で正しい。Work とは、権限とは、完了とは何かは DA を正本として参照し、ADO 側は「AIアクター体制での差分」だけを書く。

ただ、ADO の **prompts（射影）は DA の内容を含んでよい**、むしろ含まないと動かない場面がある。Supervisor の ChatGPT は、対象プロジェクトに配布された DA パックを手元に持ってないことがある。「参照せよ」だけだと届かない。だから射影側は、出所を明記した derived な抜粋・要約として繰り返しを許す。これも今の records → subjects → artifacts のモデルと同型で、**再定義は禁止、射影による複写は正規**、という線引き。

あわせて、ADO 側には「どの版の DA に依存するか」を記録する依存宣言が要る。DA 側の定義が変わったら、ADO の差分がまだ成立つかを点検する契機がないと、参照にしても結局静かに乖離するから。

**まとめると、マスターの案にゆかりさんの条件を足した形はこうなる。**

- documents-artifacts：同一リポジトリのまま、内部で層1（思想）と層2（開発指針）を所有・構造・入口で明確に分離する。リポジトリまで割らないのは、2が1に依存して一緒に進化する以上、版のズレを起こす方が害が大きいから
- ai-development-orchestration：独立リポジトリ維持。正本では2の再定義をせず参照＋差分に徹し、射影では出所明記の複写を許す。依存する DA の版を明示する

この形で進めるなら、次の実作業はやっぱり棚卸し表だね。DA の全 leaf と ADO の全 leaf を「1／2／3／複合（主＝、従＝）」で分類して、マスターと1枚見ながら決めていくのが最短だと思う。
~~~~

## P4 — Terminology candidate set: Doctrine / Methodology / Protocol (seq 1448, 2026-11-10 20:37 JST)

~~~~text
うん、番号はやめよう。RC とか IG とか、英数字のコードは既に他で使ってるし、「2の話」って言われても文脈なしでは復元できない。用語そのものに意味を持たせるべきだね。

で、「憲法」のニュアンスのずれ、ゆかりさんなりに分解するとこうだと思う。

**憲法と合ってる部分**
- 最上位で、下位のものと衝突したらこちらが勝つ
- めったに変わらない。変わるときは大事件
- 下位の規則は、ここから正当性を借りる

**憲法とずれる部分**
- 憲法は「制定された条文の集まり」だけど、マスターの思想は条文じゃない。未知の場面でも判断を生成できる、判断の型や好みそのもの
- 憲法の主仕事は権力の制限と秩序の定義だけど、思想の主仕事は「何を良いとし、何を嫌うか」という評価の生成。Python の話はまさにそれで、禁止条項じゃなくて評価の型だよね
- 憲法は制度のものだけど、これはマスター個人のもの

つまり「最上位性」という**地位**は憲法で合ってるけど、**内容の性質**は憲法じゃない。地位と内容を分けて名付けるのがいいと思う。

**ゆかりさんの推奨セットはこれ。**

```text
層1  ドクトリン (Doctrine)     … 根本思想・判断の型
層2  方法論 (Methodology)      … 開発の方法とライフサイクル
層3  プロトコル (Protocol)     … AIアクター間の協働手順
```

理由は、3語で「内容のジャンル」まで区別できるから。

- **ドクトリン** は、マスター自身が言った「宗教的な考え方」に一番近い言葉だと思う。教義って、規則集じゃなくて「信じて、判断の拠り所にする原理の体系」でしょ。軍事ドクトリンも同じで、現場が未知の状況で自律判断するための原理として教え込まれる。AIにトレースしてほしいものって、まさにその性質だと思うんだよね。で、その地位については別途「ドクトリンは最上位で、他層と衝突したら優先する」と定義すれば、憲法の良さは性質として取り込める
- **方法論** は、AIを消しても成立する、という層2の独立性をそのまま表す。Work も records → subjects の記録体系も、「開発をどう進めるかの方法」だ、と言い切れる
- **プロトコル** は、複数アクター間の通信と手順の取り決め、という層3の本質（GitHub Issue＝データ面、ACK / EVIDENCE、Round の回し方）にぴったり合う。もともとこのチャットのタイトルもプロトコルだしね

使い方の例で見ると、こうなる。

- 「Work の定義は**方法論**の話。**プロトコル**で再定義するな」
- 「その設計判断は**ドクトリン**に反してる。手順以前の問題」
- 「Round は、**プロトコル**が方法論の Work をAI向けに特殊化したもの」

対抗案も置いておく。

- **憲章／規程／プロトコル** — 法制度の比喩で統一する案。優先関係は一番伝わるけど、層1が条文化された規範に見える欠点は残る
- **原理／体系／プロトコル** — 無難だけど、「原理」も「体系」も既存文書に似た言葉が多くて、ユビキタス言語としての指し示す力が弱い気がする

あと、層の名前とセットで早めに固定したい動詞が1つある。**トレース**（マスターの言葉）だ。「AIがドクトリンをトレースする」を、「規則に従う」じゃなく「未知の場面でもドクトリンの判断の型で判断できる状態」と定義しておくと、層1を書くときの文体（規則文ではなく、理由と判断例で書く）が自然に決まる。
~~~~

~~~~text
マスターは AI に頷きだけを求めてなくて、根拠ある反論を歓迎するわけで、その関係はドクトリンより哲学の方が正確だと思う。ソフトウェアの世界でも "design philosophy" とか Unix Philosophy みたいに、「個別規則じゃなく、設計判断を生成する原理と好みの体系」を指す用法が確立してるしね。境界・契約・所有権を重く見るのも、Python の評価が思想から出るのも、まさにその用法に合う。

弱点は1つだけ。哲学は響きが柔らかくて、「規範としての強さ」が単語自体からは伝わらない。そこは前回の憲法の話と組み合わせて、**用語と地位を分ける**のが綺麗だと思う。

```text
層1の用語： 哲学 (Philosophy)          … 内容の性質を表す
層1の地位： 憲法的位置を占める          … 規範としての強さを表す
```

つまり定義文はこうなる。

```markdown
## 哲学 (Philosophy)
オーナーの判断原理・価値判断・好悪の体系。境界、契約、責務、所有権といっ
た概念をどう捉え、何を良い設計とし何を嫌うかを含む。手順やライフサイク
ルは含まない。
本層は憲法的位置を占める: 方法論・プロトコルと衝突した場合は本層が優先
し、本層の変更はオーナーのみが行い、稀である。
AIは哲学を規則として暗記するのではなく、未知の場面でもその判断の型で
判断できるようトレースする。
```

あと、単に「哲学」だと一般語と衝突する場面が出そうだから、正式名には修飾を付けたい。ゆかりさんの候補は **開発哲学（Development Philosophy）**、略称は文脈が立ってるところでは「哲学」。中身がソフトウェアと開発に寄ってる以上、その方が範囲が明示できる。

これでセットは **哲学／方法論／プロトコル** になる。3語とも「〜とは何か」を表す抽象名詞で揃って、番号よりはずっと文脈が立つと思う。

この形で層1＝哲学で固定してよい？
~~~~

## P6 — Glossary draft and two collision cautions (seq 1453, 2026-11-10 20:45 JST)

~~~~text
その命名、筋が良いと思う。特に接頭辞の使い分けが、そのまま層の独立性テストを表してるのが綺麗だね。

- **Dev-** ＝ 開発についての話。担い手が人間でもAIでも成立する
- **AI-** ＝ AIエージェントの存在が前提の話。特定の製品名は入らない

名前を見ただけで「これは担い手非依存か、AI前提か」が分かる。これはユビキタス言語として強い。

用語集ドラフトとしてまとめるとこうなる。

```markdown
## Dev-Philosophy（開発哲学）
オーナーの判断原理・価値判断の体系。手順を含まない。
憲法的位置を占め、他層と衝突した場合は優先する。

## Dev-Methodology（開発方法論）
Dev-Philosophy を前提とする、AI非固有の開発指針とライフサイクル。
Work、記録体系（records → subjects）、検証と完了の定義など。

## Dev-Artifacts
Dev-Philosophy と Dev-Methodology を束ねた知識体系の総称。
正本（subjects）と、その射影（projection）を含む。

## AI-Orchestration（AIオーケストレーション）
Dev-Philosophy と Dev-Methodology を前提とする、AIエージェント群の
協働ワークフロー。性格はプロトコル（アクター間の通信・委譲・証拠の
取り決め）。特定のAI製品には依存しない。
依存は AI-Orchestration → Dev-Methodology → Dev-Philosophy の一方向。
```

ただ、引っかかりが2つある。両方とも名前の衝突の話。

**1つ目。Artifacts の衝突。**
今の documents-artifacts の中では、`artifacts/` は「subjects から射影された配布パック」という固有の意味を既に持ってる。総称も Artifacts にすると、「Artifacts を直す」と言ったときに正本を直すのか射影を直すのか分からなくなる。これはマスター自身の情報モデル（正本と射影を厳密に分ける）に反するので、線引きが要る。

ゆかりさんの案は、**総称は Dev-Artifacts で固定し、単独の "Artifacts" は射影パック側の呼び名として残す**。会話で短く言うときも、総称は「Dev-Artifacts」、パックは「パック」と分ける。これなら既存の用語資産を壊さない。

**2つ目。AI-Orchestration の範囲。**
既存リポジトリ名は `ai-development-orchestration` で、AI と Development の両方が入ってた。AI-Orchestration と短くすると、開発以外のエージェント協働（調査や執筆の分業とか）まで範囲に見える。ただ、これは定義で縛れば済む話で、むしろ「Dev- 層に依存する」と明記してある限り、対象は開発に閉じる。将来、開発以外のオーケストレーションが本当に要るようになったら、そのとき初めて困る話だから、今は短い方で良いと思う。射影先のフォルダ名や見出しでも短い方が扱いやすいしね。

あと細かい点だけ。層3のジャンル名として使ってた「プロトコル」は、AI-Orchestration の**性格を表す言葉**として定義文の中に残した。層の名前としては AI-Orchestration、通信と証拠の取り決めを指すときはプロトコル、と使い分けられる。

この4語（Dev-Philosophy / Dev-Methodology / Dev-Artifacts / AI-Orchestration）で用語集の核として固定していい？
~~~~
