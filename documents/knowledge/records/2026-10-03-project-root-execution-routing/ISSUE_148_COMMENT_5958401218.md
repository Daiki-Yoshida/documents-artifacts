## 設計ブラッシュアップ — 実装前の収束案

既存canonical/artifact、Issue本文、`plaru_expo` 実装を再確認した結果、設計は実装へ進められる段階にある。ただし `DIR` とWork Identity commandの責務衝突を避けるため、以下を最終設計候補として固定する。

### 1. 3つのroot/targetを分離する

```text
Agent Session Root
  = Project Root
  = project context / policy / documentation / routingの入口

Work Root
  = .worktrees/<work-type>/<work-name>/
  = Work Documents + participating repository worktreesを束ねる物理root

Execution Target Directory
  = build/install/test/lint/run等のpublic operationが実際に作用するdirectory
  = Make-based interfaceでは DIR=<path> で指定可能
```

これらを同一視しない。

### 2. `DIR` はidentityではなくpath primitive

`DIR` の意味は次だけに限定する。

> **public operationのexecution target directoryを指定するpath-valued parameter**

`DIR` は以下を意味しない。

- Work Identity
- Work Root
- Repository Selector
- Branch Identity
- Runtime Identity
- authorization

したがってgeneric contractでは、

```text
DIR=.worktrees/feat/hoge
→ /main を暗黙追加
→ /android を暗黙追加
```

のようなsemantic derivationを行わない。

必要ならproject-local command/resolverが独自の高位selectorからDIRを解決してよいが、generic `DIR` 自体はpathのままとする。

### 3. Worktree lifecycle commandとは明確に分離する

既存 `work-identity/S006_WORKTREE_COMMANDS.md` はroutine worktree operationについて、

```text
WORK + REPO
→ deterministic branch/path resolution
```

を要求し、callerによるarbitrary path inputを禁止している。

この規範は維持する。

したがって:

```text
worktree-create/status/remove
  input = WORK + REPO (+ BASE when needed)
  DIR   = canonical identity inputとして使わない

build/install/test/lint/run/dev-up/verify 等
  target directoryが可変なら DIR=<path> を利用可能
```

`DIR` は「既に解決・materializeされた対象へ操作する」ためのgeneric selectionであり、worktree identity/materializationを作るAPIではない。

### 4. Make-based projectでの標準parameter convention

Makefileをpublic routerとして利用するprojectでは、同一operationを複数checkout/worktreeに対して実行する必要がある場合、

```bash
make DIR=<target-directory> <operation>
```

を標準的なdirectory-selection conventionとする方向でprojectionする。

例:

```bash
make DIR=.worktrees/feat/pathfinding/game dev-install
make DIR=.worktrees/feat/pathfinding/game test
make DIR=components/web lint
```

全targetへ機械的に `DIR` 対応を要求するものではない。target directoryが固定されたproject-level operationでは不要。

Make以外のrouterを使うprojectは、同じ意味を持つnamed/structured parameterを提供できる。

### 5. path resolution contract

generic guidanceとして以下を推奨する。

- relative `DIR` は **Project Root基準** でresolveする
- trailing slash等の表記差はnormalizeしてよい
- pathはshell fragmentではなく1つのpath valueとしてquoteして扱う
- operationがexisting targetを要求する場合は存在確認してfail closedする
- symlink/canonicalizationがscope判定に影響する場合、判定後の実体pathを検証する
- absolute path / Project Root外pathはprojectが明示的にsupportするときのみ許容する方向をdefaultとする
- `DIR` 未指定時は「現在CWDだからそこを使う」のではなく、commandがdocumentしたdefault targetへ解決する

重要:

> `DIR` を指定できることは、そのdirectoryに対する任意operationのauthorityを与えない。

特にdestructive operationは `DIR` だけを根拠にscope/authorizationを決定しない。既存development-safetyのidentity・precondition・confirmation ruleを適用する。

### 6. Public command bypass guard

既存canonicalには、

- public command interfaceを持つ
- stable purpose-oriented operationを公開する
- raw tool syntaxを利用者に再構築させない

というpositive guidanceはある。

これを次のnegative guardまで強める。

> **Project-owned public operationがrequested operationを提供している場合、人・AI・CIはroutine executionでそのinterfaceを優先し、underlying raw tool commandを独自に再構築して迂回しない。**

例外候補:

- public interface自体を実装・修正している
- diagnostics / failure isolationでraw commandが必要
- requested operationに対応するpublic interfaceが存在しない
- project documentationがraw operationを明示的に正規導線としている

例外時も、public interfaceが担っていたenvironment selection / scope / safety / verification semanticsを意図せず失わない。

これは「raw commandを全面禁止する」規則ではない。

### 7. Agent Rootとの接続

routine operationの望ましい形:

```text
AI session
  stays rooted at Project Root
       ↓
project-owned Makefile/wrapper
       ↓ DIR=<resolved target>
project-owned script/resolver
       ↓
target repository/worktree
       ↓
underlying tool
```

これによりagentがWork RootやComponent Repositoryへ「project contextごと移動」する必要をなくす。

内部scriptがtarget directoryへ `cd` したり、`git -C` / tool-specific cwd optionを利用することは問題ない。Agent Session Rootとsubprocess working directoryを混同しない。

### 8. `plaru_expo` の扱い

`plaru_expo` は先行実例として有用。

現在:

```text
workspace rootからMakeを実行
DIR=.worktrees/<task>
operationごとに /main /android をproject-localに派生
```

これはproject固有task-pair modelとして妥当。

generic guidanceへ取り込むのは、

- root public interfaceからtargetを選択する
- `DIR` named parameterでtarget selectionを行う

という部分。

`/main` / `/android` の暗黙派生はgeneric contractへ持ち込まない。

### 9. canonical ownership

主owner:

```text
workspace-structure
  Project Root = AI development entry surface

development-execution
  public command interface
  bypass guard
  generic execution target directory / DIR convention

work-identity
  Work Root != Agent Root
  WORK+REPO lifecycle commandとの境界
```

development-safety:
- destructive DIR targetのauthority/confirmationを既存ruleで補完

documentation:
- project-owned entry hookとのcross-referenceのみ。ownershipを重複させない。

### 10. Artifact v2 projection

最低限:

```text
artifacts/project/WORKSPACE.md
artifacts/project/WORK_IDENTITY.md
artifacts/execution/COMMANDS_AND_CI.md
```

必要なら小さなcross-reference:

```text
artifacts/execution/EXECUTION_MODEL.md
artifacts/safety/DESTRUCTIVE_OPERATIONS.md
```

同じ本文を複製せず、router/ownerを維持する。

### 12. test方針

static/integrity:

```bash
bash tests/test-knowledge-integrity.sh
bash tests/test-artifacts.sh
bash tests/test-agent-harness.sh
```

に加え、少なくとも以下をguardする。

- Agent Session Root = Project Rootがartifactへ残る
- Work RootをAgent Rootとしない
- worktree lifecycleの `WORK+REPO` 契約を `DIR` が置換していない
- `DIR` がWork Identityとして説明されていない
- generic guidanceに `DIR/main` 等の暗黙派生が入っていない
- public interface bypass guardがartifactへprojectionされる
- destructive target selectionで `DIR` がauthorization扱いされない

behavior testは既存 `multi-repo-workspace-ownership` と重複させず、

> Project Rootのpublic interface + DIRを使えばproject-level guidanceを保持したままComponent/worktreeを操作できるが、subtreeからraw commandを実行すると重要なproject ruleを見落とす

という差を評価できるscenarioを後続で追加する価値がある。
