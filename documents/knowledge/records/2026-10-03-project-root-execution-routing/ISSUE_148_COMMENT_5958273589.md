## 追加設計メモ — public command interface と汎用 `DIR` selector

Project RootをAI session entry rootに固定する設計を進めると、次の追加課題がある。

> Agent自体はProject Rootから起動しても、実際のimplementation/build/test/install対象はComponent Repository checkoutやWork Root配下のrepository-specific worktreeになる。その対象を、AIがpublic command surfaceを迂回せず指定する標準窓口が必要。

### documents-artifacts現状確認

canonical:

`documents/knowledge/subjects/development-execution/S003_COMMAND_INTERFACE_AND_CI.md`

runtime:

`artifacts/execution/COMMANDS_AND_CI.md`

にはすでに以下の設計がある。

- 人・AI・CIが利用するgeneric public command surfaceをprojectが持つ
- Makefile等はpublic operation name / help / parameterのrouter
- scriptsは複雑なvalidation / orchestrationを担当
- 生のprovider/tool syntaxではなく、stable purpose-oriented operationを公開する
- local/CIはproject-managed commandへ収束させる
- named/structured parameterを使う

したがって、Make/public commandを単なる短縮入力ではなく、**project-owned execution interface**として扱う思想はcanonical/artifactに既に存在する。

一方、現状は次が十分明示されていない。

1. project-owned public operationが存在する場合、AIがそれを迂回して独自のraw command pathを組み立てない、というnegative guard
2. Project Rootからsessionを維持したまま、repository/worktree等の別directoryをpublic operationのexecution targetとして渡すgeneric directory selector
3. directory selectionとWork Identity semanticsを分離する規範

### plaru_expo調査

`Daiki-Yoshida/plaru_expo` は既にroot Makefileをexecution interfaceとして使い、`DIR=` を導入している。

例:

```bash
make DIR=.worktrees/feat/example-change docker-dev-install
make DIR=.worktrees/feat/example-change docker-dev-typecheck
make DIR=.worktrees/feat/example-change android-dev-up
```

root `AGENTS.md` でも、

- commands are run from workspace root
- Docker/Android/build/test operations use root Make targets
- task worktrees are selected through `DIR`

という導線になっている。

ただし現行 `plaru_expo` の `DIR` semanticsは完全なgeneric directory pass-throughではない。

Makefileは、

```make
NORMALIZED_DIR := $(patsubst %/,%,$(strip $(DIR)))

ifneq ($(NORMALIZED_DIR),)
MAIN_RUNTIME_APP_DIR_NAME := $(NORMALIZED_DIR)/main
ANDROID_RUNTIME_APP_DIR_NAME := $(NORMALIZED_DIR)/android
...
endif
```

としており、`DIR=.worktrees/feat/example-change` をtask Work Rootとして解釈し、operation別に `/main` / `/android` を派生する。

Git helper側も `DIR` を `.worktrees/<type>/<task>` 系に限定して正規化する。

これはplaru_expo固有のtask-pair modelには適しているが、generic artifact contractとしてはWork topologyとdirectory selectionが結合している。

### 汎用化案

Artifact側では `DIR` をWork selectorではなく、**generic execution target directory selector** と定義する方向を検討する。

概念:

```text
Agent Session Root
  = Project Root

Public Command Surface
  = Project Repository側の Makefile / wrapper

DIR
  = public operationが作用するtarget directory
  = Work Identityを意味しない
  = repository roleを意味しない
  = pathそのものを選択するgeneric parameter
```

例:

```bash
make DIR=.worktrees/feat/hoge/game dev-install
make DIR=components/game dev-test
make DIR=.worktrees/fix/foo/api lint
```

（exact path shapeは各projectのrepository/worktree modelに従う。）

重要な原則:

- `DIR` から暗黙にWork Identityを推測しない
- generic contractとして `DIR/main`, `DIR/android` 等を暗黙派生しない
- target固有の派生が必要なprojectはproject-local resolverでspecializeできる
- Work-specific create/status/remove等は引き続きWork Identity subjectのsemantic operation
- build/install/test/lint等のgeneric public operationは、resolved directoryを受け取れる
- agentは対象directoryへsession rootを移す代わりに、Project Rootのpublic interfaceへdirectoryを渡す

これにより、

```text
wrong:
  cd .worktrees/.../component
  <agent/provider/tool-specific command>

preferred:
  <Project Root>
  make DIR=.worktrees/.../component <public-operation>
```

という導線を作れる。

### 追加でcanonical化を検討する規範

`development-execution` を主ownerとして次を検討する。

1. **Public-interface preference / bypass guard**
   - project-owned public commandが対象operationを提供する場合、人・AI・CIは原則そのinterfaceを使う
   - raw underlying tool commandはdiagnostics、interface implementation、または明示的に未提供のoperation等に限定する
   - public interfaceを回避してproject policy / environment selection / safety guardを失わない

2. **Generic execution-directory parameter**
   - public operationが複数checkout/worktreeへ作用する必要がある場合、named directory selector（例: `DIR`）を提供できる
   - selectorはWork Identityとは独立したpath selection primitive
   - commandの意味は同じまま、対象directoryだけを切り替える

3. **Project Root invariantとの接続**
   - agent sessionはProject Root
   - command targetは`DIR`で別directoryを指定可能
   - session rootをtarget worktreeへ移してproject-level guidanceを失う必要をなくす

### plaru_expoとの差分

plaru_expoは有用な先行実装だが、そのままnormative exampleにはしない。

```text
plaru_expo:
DIR = task root
→ operationに応じ /main /android を派生

generic proposal:
DIR = target directory path
→ path semantics以上の意味を持たせない
```

plaru_expo自身を将来このgeneric modelへ変更するかは、このIssueのgeneric design確定後に別途判断する。

### 未確定事項

- relative pathをProject Root基準に固定するか
- absolute pathを許容するか
- Project Root外pathを許容するか
- `DIR` omitted時のdefault resolution contract
- nonexistent path / symlink / nested repository validation
- destructive operationsにも同じselectorを使う場合の追加safety gate

これらは「pathをそのまま渡せるgeneric selector」という目的を壊さない範囲で設計する。
