# Issue #189 — B案の先行AI提案（会話表示からの転記）

## Provenance

- Source: このChatGPT会話のassistant返信。ユーザーの「#189はB案で進めたい。Bundleの単位と保存条件を詳しく考えよう。」への応答
- Coverage: その返信本文1件。前後の会話全体や中間ツール出力は対象外
- Fidelity: この会話に表示された返信の本文・Markdown/DIL記述を転記したもの。機械的なChatGPT API原文エクスポートとのbyte-for-byte一致は検証していない。**再構成要約ではない**

## 本文

~~~~text
B案で進めるなら、私は **「Bundleは、1つの判断や出来事を再構築するための第0情報源の集合」** と定義するのがよいと思います。

ただし、ここで大切なのは「同じ話題の情報を全部まとめる」という意味にしないことです。

`records/` は知識を分類する場所ではなく、**後から何が議論され、何が判断されたのかを正確に検証できるようにする場所**です。

その前提で、Bundleの単位と保存条件を具体化してみます。

## 1. Bundleを何で区切るか

私の提案は、**source eventの数でも、Issue番号でも、作業期間でもなく、記録する出来事のまとまりで区切る**というものです。

例えば、同じIssueの中でも次のように分けられます。

<box border radius="lg" padding={3} gap={2}>
  <text weight="medium" size="sm">例：Issue #199 の記録単位</text>
  <box background="surface-secondary" radius="md" padding={3} gap={1}>
    **Bundle A — 問題の発見と設計判断**

    <text size="sm">ユーザーの問題提起、訂正、設計提案、Issue本文</text>
  </box>
  <row justify="center">
    <icon name="arrow-down" color="tertiary"/>
  </row>
  <box background="surface-secondary" radius="md" padding={3} gap={1}>
    **Bundle B — 実装結果と完了判断**

    <text size="sm">検証結果、レビュー、PRマージ、Issue Closeの判断</text>
  </box>
  <caption>両者は関連付けるが、後から得られた情報をBundle Aへ上書きしない。</caption>
</box>

実際、#199では初期recordと完了recordを別々に保存しました。この分け方は方向として適切です。

一方で、たとえ同じIssueに属していても、半年後に別の修正判断が発生したなら、原則として新しいrecordを作るほうがよいでしょう。

ここでの基準は **「同じrecordとして取り込むことで、その出来事の根拠関係が明確になるか」** です。

## 2. Bundleを成立させる条件

次の5条件を候補にします。

| 条件 | 内容 |
|---|---|
| 意味的なまとまり | 共通の判断・調査・検証・作業結果を説明するsource群である |
| Sourceの独立性 | 複数eventをまとめても、個々の原文と出典を区別できる |
| 保存範囲の明確性 | 全体の保存なのか、選定したevent群なのか分かる |
| 文脈の追跡性 | 短い承認・訂正が何を対象にしたのか追跡できる |
| 記録の固定性 | 取り込み後の追加判断で、過去のBundleを書き換えない |

特に重視したいのは、3番目と4番目です。

### 保存範囲は原文忠実性と分ける

例えば、ユーザーが20件発言した議論から、設計に直接関係する5件を選んだ場合。

それぞれの本文を一字一句変更しなければ、**選定した5件についての原文忠実性は保たれています**。

しかし、会話全体を保存したわけではありません。

そのため、次の2つは別々に記録すべきです。

- **Fidelity（忠実性）**：保存した本文に要約・言い換え・整形があるか。
- **Coverage（収録範囲）**：会話全体、Issue本文、選択した完全なメッセージ群など、何を対象としたか。

ただし、収録する個々のsource eventは原則全文とし、途中だけ切り抜いたものを完全なsource eventとして扱わない方針を維持します。

### 文脈を失わない

例えば、ユーザーの次の発言だけを保存しても判断の根拠が分かりません。

> OK、それで進めよう。

これが何への承認か分かるように、先行するAI提案も保存するか、既存recordにあるならそこへ参照を張る必要があります。

**発言を保存することと、判断を再構築できることは別**なので、Bundleはその関係を補完するために使えるわけです。

## 3. 保存構造はどこまで統一するか

私は、ディレクトリ構造そのものは厳密に固定しすぎないほうがよいと思います。

例えば次の形で十分です。

```text id="ryb7zs"
records/
└── YYYY-MM-DD-example/
    ├── RECORD.md
    ├── USER_MESSAGES.md
    ├── ISSUE_BODY.md
    └── REVIEW.md
```

各source eventを必ず別ファイルにする必要もありません。

`USER_MESSAGES.md` に複数の完全なメッセージを保存しても、それぞれの境界が明確なら問題ないと考えます。

一方、`RECORD.md` については、最低限の約束を作りたいです。

```yaml id="2qchq3"
record_type: source_bundle
recorded_date: "YYYY-MM-DD"
scope: "何についてのsource集合か"
```

そしてSource inventoryを付けます。

| 保存ファイル | 情報源 | Coverage | Fidelity |
|---|---|---|---|
| `USER_MESSAGES.md` | ChatGPT会話 | 選定した完全なメッセージ群 | 原文を保持 |
| `ISSUE_BODY.md` | GitHub Issue | 取得時点の本文全体 | 取得本文を保持 |
| `REVIEW.md` | GitHub PR Review | 指定レビュー1件 | 取得本文を保持 |

取得URL、source日時、取得日時、commit SHAなどは、判明している範囲で併記します。

取得できない日時やIDは無理に補わず、出所が識別できることを優先します。

## 4. Bundleは途中で成長させない

ここはかなり重要だと思っています。

Bundleを「開発が完了するまで増え続けるフォルダ」とすると、過去の記録がいつの時点の何を収録したものなのか曖昧になります。

だから、**Bundleは1回の取り込みで確定する証拠集合**と考えるのがよさそうです。

例えば、Issueを作成した際にBundle Aを保存したら、後日のPRマージ時にBundle Aへファイルを追加するのではなく、Bundle Bを作成する。

必要ならBundle BからBundle Aを参照する。

こうすれば、現在の`RECORD_MODEL.md`にある原文保存・immutable history・Decision Lineageの原則とも整合します。

ただし、転記ミスや保存漏れの修正といった、元のsourceへの忠実性を回復する変更は従来どおり例外として扱います。

## 5. 過剰な規制は避けたい

ここまでの設計でも、実際の必須項目はかなり少なくできます。

私なら以下を必須にし、それ以外は必要時の追加情報にします。

- Bundleを何の目的で収録したか。
- 含まれるsource eventとそれぞれの出典。
- どこまで収録しているか、および原文への加工の有無。
- 前提となる別のsourceが存在する場合の参照関係。

日時の細分化、hash、固定ファイル名、全event共通の細かいYAMLスキーマなどは必須にしなくてよいと思います。

GitHubの原文ならGitHubのcommitやURLで追跡できる場合もありますし、Chatには永続的なsource locatorを取得できない場合もあります。そこへ一律の要件を課すと、実務上の邪魔になりそうです。

## ここで一つ重要な設計上の選択がある

**Bundleを作るとき、ある議論の全source eventを収録することまで要求するべきか？** という問題です。

私は要求しなくてよいと考えています。

必要なsource eventを選定することは許容しつつ、その選定範囲を明示する。そして、選定した各eventの内容は原則として省略しない。

この分離が重要です。

例えば「10月12日の開発議論をすべて保存した」と宣言したなら、その範囲の完全性に責任を持つ。一方、「Issue #199の採用判断に関係するユーザーメッセージを保存した」なら、会話全体の網羅性は主張しない。

**まずこの方針についてどう思う？**

特に私は、`records/` の目的から考えると、**原文の忠実性は厳格に守る一方、どのsource eventを収録対象にするかは目的に応じて柔軟に決める**のが、最も扱いやすいバランスだと思っています。
~~~~
