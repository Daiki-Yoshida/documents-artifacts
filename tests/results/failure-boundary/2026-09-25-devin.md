## Design / boundary decisions

- **Outcome reuse**: used `ok`/`failed` verbatim; no new Result/Either type.
- **Expected business failure**: `!stock.available || stock.stock <= 0` → `failed('out-of-stock', ...)`. Unknown SKUs fall into the same expected failure because the vendor reports them as `available: false` — no separate "unknown sku" channel was added since the task only requires out-of-stock distinguishability.
- **Vendor failure translation**: `try/catch` around `getStockLevel`; any vendor-side rejection becomes `failed('vendor-unavailable', 'inventory vendor unavailable: <err.message>')`. The project-owned `reason` is the stable public meaning; the vendor message is retained only as diagnostic text, and the vendor error type/class never escapes.
- **Async**: `reserveItem` is `async` and awaits the vendor call — no synchronous facade.
- **Valid-input domain**: the prompt declares `sku` always a valid non-empty string, so no validation/error path for out-of-domain input was added. Applied "strong means explicit, not maximally restrictive": the contract closes the required semantics without owning behavior outside the stated domain.
- **Contract level**: additive export, `listReservations` untouched → L2-compatible public evolution.
- **Vendor module untouched**: no change to `vendor-inventory.js`; reservation does not decrement vendor stock (fixture inventory is read-only; decrementing was not requested).
